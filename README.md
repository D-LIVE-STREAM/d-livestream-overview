# รายงานสรุปภาพรวมและสถาปัตยกรรมของโครงการ D-LIVE Streaming

> เอกสารนี้อธิบายภาพรวมและการตัดสินใจเชิงสถาปัตยกรรมของแพลตฟอร์ม D-LIVE Streaming เพื่อใช้อ้างอิงและเผยแพร่ต่อสาธารณะ โดยไม่เปิดเผยซอร์สโค้ด ข้อมูลผู้ใช้ ค่าตั้งค่าภายใน หรือข้อมูลที่ใช้เข้าถึงระบบ

## 1. ภาพรวมของระบบ

D-LIVE Streaming เป็นแพลตฟอร์มไลฟ์สตรีมมิงที่ครอบคลุมทั้งฝั่งผู้ชม ฝั่งผู้ดูแลระบบ และแอปบนมือถือ ให้บริการแบบสมัครเป็นแพ็กเกจ ระบบจึงต้องควบคุมสิทธิ์การใช้งานได้จริง ทั้งจำนวนอุปกรณ์ที่ล็อกอินพร้อมกันและจำนวนผู้ชมต่อห้อง

ระบบแบ่งออกเป็น 6 ส่วน แต่ละส่วนเป็น Repository แยกกันและ Deploy แยกกัน

| ส่วน | หน้าที่ | เทคโนโลยีหลัก |
|---|---|---|
| API | ตรรกะหลักของระบบ บัญชีผู้ใช้ สิทธิ์ และห้องไลฟ์ | Node.js, Express, MongoDB |
| เว็บผู้ชม | หน้าเว็บสำหรับสมัครสมาชิกและรับชมไลฟ์ | React, Redux Toolkit, Vite |
| หลังบ้าน | เครื่องมือของผู้ดูแลระบบ รวมถึงมอนิเตอร์สตรีม | React, Vite, SRS WebRTC |
| แอปมือถือ | แอป iOS และ Android | Flutter |
| Media Proxy | รวมช่องทางของ Media Server ไว้หลัง Origin เดียว | Koa, SRS |
| API Gateway | ชั้นหน้าสุดของ API | Kong, Konga |

## 2. สถาปัตยกรรมการสตรีม

การตัดสินใจที่กำหนดรูปร่างของระบบมากที่สุดคือ **การเลือกโปรโตคอลสตรีมตามบทบาทของผู้ใช้ แทนการใช้โปรโตคอลเดียวทั้งระบบ**

### 2.1 ฝั่งผู้ชม — HTTP-FLV

ผู้ชมทั่วไปรับชมผ่าน HTTP-FLV ซึ่งวิ่งบน HTTP ปกติ จึงผ่าน Proxy และเครือข่ายองค์กรได้โดยไม่ต้องตั้งค่าเพิ่ม และรองรับเบราว์เซอร์ได้กว้างกว่าทางเลือกอื่นในขณะนั้น ความหน่วงสูงกว่า WebRTC แต่อยู่ในระดับที่ยอมรับได้สำหรับการรับชมทั่วไป

### 2.2 ฝั่งผู้ดูแล — WebRTC

หน้าหลังบ้านฝังตัวเล่น WebRTC ของ SRS เพราะผู้ดูแลต้องตรวจคุณภาพสตรีมและตอบสนองต่อปัญหาได้ทันที ความหน่วงที่ต่ำกว่าจึงคุ้มกับการตั้งค่าที่ยุ่งกว่า ข้อแลกเปลี่ยนที่ตามมาคือ WebRTC ต้องทำงานภายใต้ Secure Context เท่านั้น การพัฒนาหน้าหลังบ้านจึงต้องรันผ่าน HTTPS ตั้งแต่บนเครื่องนักพัฒนา

### 2.3 Media Proxy

Media Server เปิดบริการหลายช่องทางคนละพอร์ต ทั้งช่องสัญญาณของ WebRTC และไฟล์สตรีมสำหรับเล่น (FLV และ HLS) หากให้ Client เรียกตรง จะเจอปัญหาสามอย่าง คือต้องรู้พอร์ตของแต่ละช่องทาง ติด CORS และติด Mixed Content เมื่อหน้าเว็บเป็น HTTPS

ระบบจึงวาง Proxy ที่เขียนด้วย Koa ไว้ด้านหน้า แล้วรวมทุกช่องทางไว้หลัง Origin เดียว ฝั่ง Client เรียกทุกอย่างจากที่เดียวกัน และเปลี่ยนปลายทางได้ผ่านค่าตั้งค่าโดยไม่ต้องแก้โค้ด

## 3. ฝั่ง API

- **Express กับ MongoDB (Mongoose)** จัดกลุ่มโค้ดเป็น Controller และ Model แยกตามขอบเขตของข้อมูล ได้แก่ ผู้ใช้ ลูกค้า สิทธิ์การใช้งาน ห้องไลฟ์ รายการใช้งาน การยืนยันด้วย OTP และค่าตั้งค่าระบบ
- **ยืนยันตัวตนด้วย JWT** และเข้ารหัสรหัสผ่านด้วย bcrypt
- **OTP ทางอีเมล** สำหรับการสมัครสมาชิกและการกู้รหัสผ่าน
- **Docker และ GitHub Actions** สร้างและเผยแพร่ Image อัตโนมัติเมื่อมีการเปลี่ยนแปลงโค้ด

### 3.1 การจำกัดจำนวนอุปกรณ์

บริการที่ขายเป็นแพ็กเกจมักเจอการแชร์บัญชีต่อกัน ระบบจึงต้องรู้ว่าบัญชีหนึ่งมีอุปกรณ์ใดใช้งานอยู่บ้าง และตัดอุปกรณ์ที่เกินโควตาออกได้

หลักที่ยึดคือ **การบังคับสิทธิ์ทั้งหมดเกิดที่เซิร์ฟเวอร์** เพราะการตรวจที่ฝั่งแอปหรือเบราว์เซอร์ถูกข้ามได้เสมอ การจำกัดจำนวนผู้ชมต่อห้องก็ใช้หลักเดียวกัน

## 4. ฝั่งเว็บผู้ชม

- **React กับ Redux Toolkit** สำหรับสถานะผู้ใช้และสถานะการรับชม
- **Vite และ Tailwind CSS**
- **Sentry** เพื่อให้เห็นข้อผิดพลาดที่เกิดกับผู้ใช้จริง แทนการรอให้ผู้ใช้แจ้งเข้ามา
- **App Links ของ Android และ Universal Links ของ iOS** เพื่อให้ลิงก์ที่แชร์ออกไปเปิดเข้าแอปมือถือได้โดยตรงแทนที่จะเปิดเบราว์เซอร์

## 5. แอปมือถือ

แอปออกแบบเป็น **Hybrid** โดยแบ่งตามความต้องการของแต่ละหน้าจอ

- หน้าที่ต้องการประสบการณ์แบบ Native ได้แก่ การสมัครสมาชิก เข้าสู่ระบบ ยืนยัน OTP กู้รหัสผ่าน และการสมัครแพ็กเกจ ทำเป็นหน้าจอ Native
- การรับชมไลฟ์ฝังเว็บผู้ชมผ่าน WebView เพื่อไม่ต้องดูแลตัวเล่นสตรีมสองชุดที่ต้องตามแก้พร้อมกันทุกครั้งที่ฝั่งสตรีมเปลี่ยน
- รองรับ **Picture-in-Picture** ให้ผู้ชมดูต่อได้ขณะสลับไปใช้แอปอื่น
- จัดการเส้นทางภายในแอปด้วย `go_router` และเก็บสถานะการเข้าสู่ระบบด้วย `shared_preferences`

## 6. สรุปบทเรียนเชิงสถาปัตยกรรม

1. **เลือกโปรโตคอลตามผู้ใช้ ไม่ใช่เลือกตัวเดียวให้ทั้งระบบ** ผู้ชมต้องการความเข้ากันได้กว้าง ผู้ดูแลต้องการความหน่วงต่ำ การบังคับให้ใช้เหมือนกันทำให้ฝั่งใดฝั่งหนึ่งเสียประโยชน์
2. **รวมปลายทางไว้หลัง Origin เดียว** ช่วยตัดปัญหา CORS, Mixed Content และการผูกพอร์ตไว้ในโค้ดฝั่ง Client ออกไปพร้อมกัน
3. **สิทธิ์ทุกอย่างบังคับที่เซิร์ฟเวอร์** สิ่งที่ตรวจเฉพาะฝั่ง Client ถือว่าไม่ได้ตรวจ
4. **เลือก Hybrid เมื่อการดูแลโค้ดสองชุดแพงกว่าประสบการณ์ที่ได้เพิ่ม** ส่วนที่ผู้ใช้สัมผัสบ่อยและต้องการความลื่นไหลทำเป็น Native ส่วนที่เปลี่ยนบ่อยตามฝั่งสตรีมใช้ WebView
